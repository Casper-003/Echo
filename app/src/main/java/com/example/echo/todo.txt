# BEV 扫描底图 技术路线 TODO
更新时间：2026-04-06

## 背景
用户希望通过手机摄像头扫描房间，自动生成可作为地图底图的俯视图（BEV）。
入口已在 MapVerificationScreen 工具栏预留（AI 扫描按钮，当前 enabled=false）。
生成的图片路径与相册选图入口完全一致，均通过 bgImageUri 存储。

---

## 分阶段技术路线

### 阶段一（短期可实现）：语义分割 + IPM

原理：
  1. 用手机摄像头拍摄地面多帧（引导用户缓慢平移）
  2. MobileNetV3-Small（TFLite 量化版，~8MB）逐帧对图像做语义分割，提取"地板"像素掩码
  3. 根据陀螺仪姿态矩阵（Rotation Vector Sensor）计算相机到地面的单应矩阵，做逆透视变换（IPM）将每帧展平为俯视图
  4. ORB 特征点匹配，将多帧俯视图拼接对齐，覆盖 map.width × map.length 的物理范围
  5. 输出 JPG，回调至 MapVerificationScreen.bgImageUri（与相册选图接入点完全相同）

优点：模型小、速度快、无需网络、工程链路清晰
缺点：被家具遮挡的地板区域为空洞（黑色），不做脑补

模型参考：
  - TFLite MobileNetV3-Small（ADE20K 室内场景预训练）
  - 模型体积：~8MB，推理耗时：~100ms/帧（骁龙 8 系）

关键 Android API：
  - CameraX（相机帧获取）
  - SensorManager TYPE_ROTATION_VECTOR（姿态矩阵）
  - org.tensorflow:tensorflow-lite（TFLite 推理）
  - OpenCV Android SDK（IPM 变换、ORB 拼接）或纯 Kotlin 实现单应矩阵

---

### 阶段二（长期目标）：端到端 BEV 深度学习模型

原理：
  - 输入：绕房间一圈拍摄的连续帧序列（约 60~120 帧）
  - 模型：RoomFormer（室内专用，Transformer 架构）或 Pano2BEV 类模型
  - 输出：带语义标注的俯视 RGB 图（墙体/地板/家具语义色块）
  - 模型可"脑补"被遮挡区域（如床底下的地板），效果最佳

优点：效果上限最高，遮挡区域合理填充，语义清晰
缺点：
  - RoomFormer 尚无官方 TFLite/ONNX 版本，需自行转换和量化（PyTorch → ONNX → TFLite）
  - 目标模型体积 <50MB，推理时间 1~3 秒
  - 需要用户配合绕房间一圈拍摄

参考资料：
  - RoomFormer：https://github.com/ywyue/RoomFormer
  - Metric3D（单目深度，作为辅助方案）：https://github.com/YvanYin/Metric3D

## 工程接入点（已预留）

文件：MapVerificationScreen.kt
位置：工具栏 "AI 扫描" 按钮（当前 enabled=false）
注释标记：// TODO: BEV_SCAN 入口

接入方式：
  - 点击按钮 → 启动 BevScanActivity（待创建）
  - BevScanActivity 完成扫描后 → 通过 ActivityResultLauncher 回调图片 Uri
  - 回调中执行与相册选图相同的逻辑：bgImageUri = uri; bgScale = 1f; bgOffset = Offset.Zero

---

## 数据存储约定

- 底图存储路径：context.filesDir/maps/{mapId}/bg.jpg
- 存储字段：MapEntity.bgImageUri（绝对路径字符串）
- 偏移字段：MapEntity.bgOffsetX / bgOffsetY（米，双指拖动后持久化）
- 透明度：不持久化，固定 0.35f（精修界面可临时调节但不写入 DB）

---

## 注意事项

1. 阶段一的 IPM 精度依赖相机内参（焦距、主点），需在扫描前做一次简单标定或使用手机默认出厂参数（Camera2 API 可读取）
2. 多帧拼接时需要防止累积误差，建议以地图四角 AR 锚点为基准做全局对齐
3. 阶段二模型量化后精度可能下降，建议在量化前用 ADE20K 室内子集评估 mIoU
4. 两个阶段的输出格式完全一致（JPG），对 MapVerificationScreen 透明，只需替换 BevScanActivity 的内部实现即可
